What “create your own model” means here

We adapt an existing model, rather than pretrain a language model from random weights. You will produce your own LoRA adapter and merged weights. The knowledge base remains a separate, updatable source of facts. Browser demos are explicitly labeled simulations; actual training runs in Python.

01 / CHOOSE YOUR APPROACH

Give it a book, a lesson, or a whole education?

Keep one distinction in mind: facts and behavior need different tools.

RAG · open-book exam

Retrieve knowledge

Find passages and insert them into the prompt. Model weights stay unchanged.

Best for release rules, internal APIs and frequently changing documentation. Sources can be inspected.

Fine-tuning · practice

Teach a behavior

Update a small set of weights using examples of the answers you want.

Best for consistent format, terminology or a specialized task. Does not guarantee factual recall.

Pretraining · education

Learn language from scratch

Train all weights on a very large corpus using next-token prediction.

Requires far more data and compute. A small team handbook cannot teach general language ability.

Which approach fits?Decision lab

Our project combines retrieval + a small LoRA adapter. Qwen2.5-0.5B-Instruct is a compact instruction-following model with about half a billion parameters and an Apache-2.0 license. It is selected for a small, understandable guide, not because it is the strongest coding model. Model card ↗

Remember: RAG changes what the model reads. Fine-tuning changes how it responds. Pretraining builds the underlying language capability.
02 / INSIDE A LANGUAGE MODEL

A very capable next-token predictor.

Text becomes token IDs. Embeddings turn those IDs into vectors. Attention mixes information from earlier tokens; feed-forward layers transform it. A final layer assigns a score to each possible next token. Generating repeats this loop.

Retrytherequestwith…

Lower = sharper probabilities. Higher = more variety. These word chips and logits are invented for teaching; real token boundaries can split words.

Try changing temperature, then sample several times.

Training: compare and correct

Given “retry with exponential”, predict “backoff”. The loss is −log P(correct token). Backpropagation computes gradients; an optimizer adjusts trainable weights to reduce loss.

One epoch means one pass over the training examples. A batch is a group of examples per step. Learning rate controls update size.

Inference: predict and append

There is no optimizer at inference time. The model appends a token, then predicts the next. A context window limits how much it can read at once.

For Java developers: weights resemble a trained artifact loaded by a runtime. A prompt is input data; it does not recompile the model.

03 / PREPARE THE KNOWLEDGE

Good data is the first model improvement.

DevGuide helps engineers at the fictional company Acorn. Its handbook covers safe retries, API errors, database migrations, testing and releases. These are sample company policies, not universal engineering rules.

Understand before you implement

What is a knowledge base, exactly?

A knowledge base is a collection of information you trust. For Acorn, it is the team's written engineering rules. It can start as a few Markdown files; it does not need to be a special database. Our kb.json simply holds a list of passages with labels.

Acorn handbook · our running example

Safe HTTP retries

For transient HTTP 429 or 503 responses, retry at most 3 times with exponential backoff and jitter. Honor Retry-After. Retry POST only with an idempotency key.

Source: retry-v1Revision: 2026-01-01

Suppose a developer asks, “May I retry a failed POST?” A generic model may know what POST means, but it has not necessarily seen Acorn's rule. Your job is to connect this particular rule to that question.

Explicit knowledge: readable text

The handbook says “at most 3”. You can open the file, inspect the sentence and change it. Retrieval searches this external information.

Learned knowledge: model weights

A trained model stores distributed numerical patterns that influence token predictions. There is no addressable “retry policy” row inside its weights. Training may teach facts, but it cannot guarantee exact recall or freshness.

Does saving a document create a model? No. Saving creates data. Indexing makes data searchable. Training changes numerical weights. These are three different operations.

One handbook becomes two different ingredients

Think of teaching a new teammate. You give them a reference book so they can check the rules, and worked examples so they learn how to explain those rules. DevGuide uses both.

Why each preparation step exists

1 · Collect and clean

Agree on what is true before teaching it

If an old page allows 5 retries and the current page allows 3, keeping both without a version rule makes the answer ambiguous. Keep the approved current passage, preserve the original meaning and record the source. Removing a password protects it; removing the word “only” changes the policy.

2 · Give each passage an address

Metadata makes answers traceable

Text contains the rule; id identifies it; title helps humans and search; revision says which version it is. The string [retry-v1] in an answer should point back to this record. A citation marker by itself does not prove the answer is correct.

id → retry-v1title → Safe HTTP retriestext → the full rule
3 · Split into meaningful chunks

A chunk is a passage that can stand on its own

A whole handbook wastes prompt space. A sentence fragment loses meaning. Keep the retry limit, applicable status codes and POST condition together. In a larger handbook, split at topic headings; add modest overlap only when useful context crosses a boundary.

A harmful split

Chunk A: “Retry POST …”
Chunk B: “… only with an idempotency key.”

Retrieving A alone hides the condition.
A useful chunk

“Retry POST only with an idempotency key.”

The action and its condition travel together.
4 · Write reviewed teaching examples

A fact is not yet a training task

Make the desired behavior explicit: input = instruction + evidence + question; target = the answer a reviewer wants. For “May I retry POST?”, the target must preserve “only with an idempotency key”. It also demonstrates our four answer labels.

Prompt: what the model sees

Instruction: answer from evidence.
Evidence: [retry-v1] the full retry rule.
Question: May I retry POST?

Completion: what it should learn to produce

Rule: POST requires an idempotency key.
Why: The policy requires that condition.
Check: Follow the retry limit and delays.
Source: [retry-v1]

JSON is one structured record. JSONL is many JSON records, one per line. During training, token IDs represent the prompt and answer; the loss in this project is computed on the completion.

5 · Separate practice from exams

Test transfer, not recognition of a copied answer

Training examples update weights. Validation examples help choose settings and checkpoints. A frozen test set judges the finished experiment. Put all paraphrases of a policy topic in one split.

Practice: retries, errors, tests, logsRehearsal: migrationsFinal exam: releases

Release passages remain in the knowledge base at evaluation time: this tests whether the model can answer from a policy it did not practice in fine-tuning. The held-out release answers are not training targets.

Now the implementation has a purpose

prepare.py writes the reference book and practice/exam records. It creates no model weights and no search index. Chapter 04 builds the index; chapter 05 trains the adapter.

Implementation checklist: prepare the files

  1. Collect approved sources. Use Markdown docs, reviewed runbooks and API specifications. Remove credentials, customer data, stale copies and contradictory policies.
  2. Keep provenance. Give every section an ID, a title and a revision. A citation is useful only if someone can find the passage.
  3. Chunk by meaning. Keep a rule and its exceptions together. Try 200–400 tokens for larger documents, then measure retrieval. Our tiny handbook uses one section per chunk.
  4. Separate evidence from teaching examples. kb.json contains facts. Training JSONL contains prompts and desired completions. The completion teaches a “Rule / Why / Check / Source” format.
  5. Split before generating paraphrases. Hold out whole policy topics or document families. Similar rewrites of one answer across splits leak information.
Inspect the source → teaching exampleEditable knowledge lab

Changing the passage changes this preview only. Write a new, human-reviewed completion that matches your edited policy before adding it to the training set. It is not automatically fact-checked.

Small starter data ≠ a proven specialist

The kit generates 16 training and 4 validation records, plus 5 held-out test questions. This is enough to exercise the pipeline, not to establish improvement. For a useful model, begin with a few hundred diverse, reviewed examples; scale based on measured failures. There is no magic example count.

What does a good training example look like?

The prompt includes evidence and a question. The completion uses only that evidence and cites its ID. Include unanswerable questions with an explicit “I don't know” target. Teach concise explanations, not hidden chains of thought. LoRA can learn the response pattern while retrieval supplies new policies.

Our split uses retries, errors, tests and logging for training; migrations for validation; releases for held-out answerable tests. Unknown-topic and malicious-instruction tests stay outside training. Keep the test set frozen after you begin comparing models.

04 / BUILD A RETRIEVAL ASSISTANT

Let the model look up the answer.

Retrieval-augmented generation (RAG) finds relevant passages, attaches them to the question and asks the model to answer with evidence. We use TF-IDF + cosine similarity for a transparent local baseline. It matches weighted words; it does not understand synonyms the way a good embedding retriever can.

Understand before you implement

What is a retrieval assistant?

Imagine asking an engineer a question. They find the right handbook page, read it beside your question, and explain the answer. A retrieval assistant separates those same jobs between a search component and a language model.

R · Retrieval

Find the passage about POST retries among the handbook sections.

Output: source text and its ID.

A · Augmentation

Add that passage to the model's input, beside the question and instructions.

Output: an evidence-filled prompt.

G · Generation

Use the language model to write an answer, one token at a time.

Output: answer text to verify.
Where is knowledge retrieved from?

In this project, the retriever searches documents outside the language model. The model then reads the selected text. When a model answers from its weights alone, it generates from learned patterns; it is not fetching a stored document or a guaranteed factual record.

Before the first question: build a searchable index

An index is a representation that makes searching easier. Here it is a matrix: one row per passage, one column per vocabulary feature. It is closer to a search engine's lookup structure than to a newly trained language model.

A · Represent words as numbers

A vector is just an ordered list of numbers

For a tiny illustration, choose four columns: [retry, post, logs, canary]. A passage mentioning retry and POST becomes [1, 1, 0, 0]. A 1 means the word is present. Every passage and question must use the same column order.

The real script uses richer weights. TF measures term frequency in a passage. IDF gives more weight to terms that occur in fewer passages. A rare term such as “idempotency” can help identify a specific policy. Word pairs such as “retry post” add local context. TF-IDF reference ↗

B · Compare the question with each passage

Similar directions suggest related vocabulary

Cosine similarity compares vector directions: multiply corresponding entries, add them, then divide by both vector lengths. For nonnegative word vectors, 1 means the same direction, and 0 means no shared features. It measures overlap, not truth.

similarity(q, d) = (q · d) / (length(q) × length(d))

Question [1,1,0,0] vs retry passage [1,1,0,0]: 2 / (√2 × √2) = 1. Against logging [0,0,1,0]: the dot product is 0. A zero query vector has no direction; our demo treats it as no match. Cosine reference ↗

These four columns omit most real words. The toy lab explains vector comparison; it is not the index used by the Python script or the lexical playground below.

C · Retrieve the top-k passages

Pick evidence, then fetch its original text

Top-k means “keep the k highest-ranked matches”. With k = 2, you keep up to two passages. The vector points to a record; the model receives that record's text, not the TF-IDF array. Our implementation drops zero-score matches. A positive score does not guarantee the passage answers the question.

If the question is “What is our release password?”, a release passage may match “release” yet contain no password. The model should still say it does not know. If there are no matches at all, our application returns that message before calling the model.

D · Assemble a prompt

Give the model a small, relevant reading packet

System instruction

Answer only from evidence. Use Rule / Why / Check / Source. If the answer is missing, say you do not know.

Retrieved evidence

[retry-v1] For transient HTTP 429 or 503 responses, retry at most 3 times … Retry POST only with an idempotency key.

User question

May I retry a failed POST?

This is temporary context for a single request. A chat template wraps the messages in the model's expected role markers; its tokenizer then converts the whole packet into token IDs.

E · Generate and check

The model composes; it does not paste a guaranteed answer

The model processes the prompt, predicts a next-token distribution and appends a chosen token. It repeats until it stops or reaches the output limit. Attention lets predictions depend on earlier prompt tokens, including the retrieved passage. No gradient update happens in this loop.

An adapter can favor the answer style practiced during training. Neither the adapter nor retrieval makes every output true. Check that “only with an idempotency key” survived, the retry limit is correct, and the citation actually supports the claim.

Two vocabularies, two different jobs. The retriever's feature vocabulary helps search documents. The language model's tokenizer vocabulary helps read and generate text. The TF-IDF search vector is not a model embedding, and it is not sent to Ollama as the prompt.

How to upgrade retrieval when the baseline fails

Try a semantic embedding model for synonym-heavy questions, then hybrid lexical + semantic retrieval and a reranker. Preserve chunk IDs and source metadata. Enforce document permissions before retrieval; never give this tutorial assistant tools that execute commands. Test malicious passages and questions separately.

Theory → implementation

Training needs a different kind of work

Inference makes predictions with fixed weights. Training also tracks gradients and updates trainable parameters, so it needs additional libraries and memory.

Use a compatible PyTorch installation first; then install the pinned trainer stack. This script runs the separate weight-learning stage.

Theory → implementation

Versions are part of an experiment

A training configuration depends on the library interfaces implementing it. A version list helps another developer recreate those interfaces.

These pins describe the teaching environment. Hardware-specific PyTorch installation and the recorded final environment complete the setup.

This is ordinary LoRA, with float16 GPU base weights, not QLoRA. QLoRA additionally quantizes the frozen base during training and requires compatible tooling. Avoid that complexity for the first run.

Theory → implementation

How examples become your own adapter

For each prompt and reviewed completion, the model predicts answer tokens. Completion-only loss measures how unlikely the target tokens were. Gradients and the optimizer update the LoRA matrices.

Training repeats over the practice split. Validation selects a checkpoint; the adapter directory stores the learned changes. The frozen base and external handbook remain distinct artifacts.

What the knobs do

Rank 8: small adapter capacity.
Learning rate 2e−4: a starting experiment, not a universal optimum.
Length 512: caps memory; check for truncation.
Batch 1 × accumulation 4: effective batch 4 on one device.
3 epochs: a smoke-test duration, not a quality promise.

What comes out

adapter/ contains the LoRA weights, adapter configuration and tokenizer. It still needs the original base model. merged/ is created in the next chapter and contains standalone combined weights.

Completion-only loss teaches the answer rather than scoring the evidence text. The script uses prompt/completion records and the tokenizer's chat template.

API basis: TRL 0.21 SFTTrainer and Transformers chat templates. The exact dependency stack and GPU execution should be smoke-tested on your hardware before scaling.

When training fails

CUDA out of memory: reduce max_length to 256 and inspect that targets still fit; keep batch 1, enable gradient checkpointing (already on), close other GPU jobs. Quantized training is a later option.

Unexpected keyword: check pip show trl transformers peft. Older tutorials use different argument names. Use this kit's pins in a clean environment.

Loss decreases but answers worsen: review labels, leakage and overfitting. Choose checkpoints using validation results. Test the base model too: a tiny dataset may make it worse.

A model repository holds weights, configuration and tokenizer files. Uploading those files makes them available to a runtime that can load them.

A defensible improvement loop

Freeze a baseline → label failures → change one thing → compare on development data → run the frozen test set for a release decision. Report numerators and denominators: “4/5” tells you more than “80%” alone. Five examples cannot establish production reliability; add diverse unseen questions, expert review and repeated latency measurements.
